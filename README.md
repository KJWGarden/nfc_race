# CHECKPOINT — NFC 워킹 레이스

걸어서 정해진 지점마다 NFC를 태깅하고, 참가 팀 순위로 시상하는 운영/참가 앱입니다.

관리자 뷰와 참가자 뷰가 분리되어 있습니다. 참가자는 자기 팀 현황만 볼 수 있습니다.

- 스택: Next.js 16 (App Router) · React 19 · TypeScript · Tailwind CSS 4 · Supabase(Postgres, Realtime)
- 배포 대상: Vercel + Supabase
- 규모: 참가자 100~300명 기준

## 역할

### 관리자
- 참가 세션 CRUD, 지점 수/시상 순위 수 지정
- 세션별 참가자 명단, 실시간 현황, 순위, 완주 시간 (Supabase Realtime으로 즉시 갱신)
- 초대 링크/QR
- NFC 지점 생성, NTAG 424 DNA 태그 등록·기준값 갱신, SDM 설정값/태그별 키 조회
- 실시간 공지
- 시상 화면 CTA (`시상 화면 띄우기`)

### 참가자
- 세션 코드 또는 초대 QR로 참가
- 팀장이 팀 생성 → 팀 코드로 팀원 참가
- 우리 팀 레이스만 표시 (다른 팀 현황 비공개), 10초마다 자동 갱신 (탭이 숨겨지면 멈춤)
- 팀원 한 명이 태그를 찍으면 팀 전체가 인정됨
- 쿠키를 잃었을 때 "다시 들어가기"로 기존 참가자 복귀

## 데이터 저장

모든 데이터는 Supabase Postgres에 저장됩니다. 스키마는 `supabase/migrations/`의 SQL 파일이 정의합니다.

- 모든 테이블은 RLS가 켜져 있고 익명(anon) 키로는 읽기·쓰기·함수 호출이 모두 막혀 있습니다. 앱 서버만 service_role 키로 접근합니다.
- 예전 버전이 쓰던 `data/db.json`은 더 이상 사용하지 않습니다. 파일이 남아 있어도 앱은 읽지 않습니다.

## 로컬 개발

필요: Node.js 24, Docker, Supabase CLI

```bash
cd ~/dev/nfc-walk-race
npm install
supabase start          # 이 프로젝트는 기본 포트와 겹치지 않게 554xx 포트를 씁니다 (API 55421)
supabase db reset       # 마이그레이션 + supabase/seed.sql (DEMO01 데모 세션) 적용
supabase status -o env  # 로컬 키 확인
cp .env.example .env.local   # 값 채우기 (아래 표 참고)
npm run dev             # http://localhost:3000
```

- 참가자: http://localhost:3000
- 관리자: http://localhost:3000/admin/login (개발 모드 기본 비밀번호 `admin123`)
- 데모 세션 코드: `DEMO01` (로컬 seed 전용. **운영 DB에는 seed.sql을 절대 실행하지 마세요.** 고정 태그 코드가 들어 있습니다)

테스트 도구:

```bash
npm run test:sun   # SUN 암호 검증 테스트 (NXP AN12196 예시 값)
# 태그 없이 SUN URL 만들기 (개발용, .env.local 의 SUN 키 사용)
node --env-file=.env.local scripts/sun-url.ts --uid 04A1B2C3D4E5F6 --ctr 12 --origin http://localhost:3000
```

## 환경 변수

`.env.example`에 전체 목록이 있습니다.

| 변수 | 공개 여부 | 설명 |
|---|---|---|
| `SUPABASE_URL` | 서버 전용 | Supabase API URL |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버 전용 | service_role 키. DB 전체 권한 |
| `SUPABASE_JWT_SECRET` | 서버 전용 | 관리자 Realtime 토큰 서명용 JWT secret |
| `APP_SECRET` | 서버 전용 | 쿠키 서명 비밀값 (`openssl rand -hex 32`) |
| `ADMIN_PASSWORD` | 서버 전용 | 관리자 비밀번호 |
| `SUN_META_KEY` | 서버 전용 | 태그 SDM 메타 읽기 키 (32 hex, `openssl rand -hex 16`) |
| `SUN_MASTER_KEY` | 서버 전용 | 태그별 파일 읽기 키의 마스터 (32 hex). **가장 민감한 값** |
| `NEXT_PUBLIC_SUPABASE_URL` | 브라우저 공개 | Supabase API URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 브라우저 공개 | anon 키 또는 `sb_publishable_…` 키 |

주의:

- `NEXT_PUBLIC_SUPABASE_ANON_KEY`에 service_role 키나 `sb_secret_…` 키를 넣으면 DB 전체 권한이 브라우저로 나갑니다. 반드시 anon/publishable 키를 넣으세요.
- `SUN_META_KEY` / `SUN_MASTER_KEY`는 실물 태그 설정에 쓰입니다. 바꾸면 모든 태그를 다시 설정해야 하므로 비밀번호 관리자 등에 따로 보관하세요.
- **운영(production) 빌드에서는 `ADMIN_PASSWORD` 또는 `APP_SECRET`이 비었거나 기본값(`admin123`, `checkpoint-dev-secret`)이면 모든 API가 503을 반환합니다.** 개발 모드(`npm run dev`)에서는 기본값을 그대로 쓸 수 있습니다.
- 개발 도구 캐시(`.next/cache`, `.next/dev/cache`)에 환경 변수 값이 남을 수 있습니다. git에는 포함되지 않지만, 필요하면 삭제하세요.

## 운영 Supabase 준비

1. Supabase 프로젝트를 만듭니다. 리전은 참가자와 가까운 곳(예: 서울 `ap-northeast-2`)을 고릅니다.
2. `supabase/migrations/`의 SQL 파일을 **파일 이름 순서대로** 적용합니다.
   - 방법 A (새 프로젝트): `supabase link --project-ref <ref>` 후 `supabase db push`. seed는 적용되지 않습니다.
   - 방법 B: 대시보드 SQL Editor에 파일 전체를 붙여 넣고 파일마다 한 번씩 실행.
   - SQL Editor로 적용한 프로젝트는 마이그레이션 기록이 남지 않습니다. 이후 `db push`를 쓰려면 먼저 `supabase migration repair --status applied <버전>`으로 이미 적용한 버전을 표시하세요.
3. Realtime 설정에서 "Allow public access"를 끄는 것을 권장합니다. 관리자 알림은 비공개 채널로만 전송되지만, 공개 채널을 막아 두면 더 안전합니다.
4. 관리자 Realtime은 앱 서버가 프로젝트의 JWT secret(HS256)으로 서명한 토큰을 씁니다. 프로젝트를 비대칭 서명 키로 전환하거나 기존 JWT secret을 폐기하면 관리자 화면의 실시간 갱신이 멈춥니다(새로고침으로는 계속 볼 수 있음).
5. 운영 데이터가 들어가기 전에 키가 노출된 적이 있다면 service_role 키/JWT secret을 교체하세요.

## Vercel 배포

1. 이 저장소를 Vercel 프로젝트로 가져옵니다 (Framework: Next.js, 기본 빌드 설정 그대로).
2. Settings → Environment Variables에 위 표의 변수를 모두 넣습니다.
   - `ADMIN_PASSWORD`, `APP_SECRET`은 반드시 기본값이 아닌 새 값으로 넣으세요. 기본값이면 배포 후 모든 API가 503입니다.
   - **Preview 배포도 production 모드로 동작**하므로 Preview 환경에도 같은 규칙이 적용됩니다.
   - `NEXT_PUBLIC_*` 값은 빌드할 때 번들에 고정됩니다. 값을 바꾸면 다시 배포해야 합니다.
3. Functions 리전을 Supabase 리전과 가깝게 맞춥니다 (예: Supabase 서울 ↔ Vercel `icn1`).
4. 도메인을 정한 뒤에 태그를 설정하세요. 태그에는 `https://<도메인>/t/s?...` URL이 기록되므로 도메인이 바뀌면 모든 태그를 다시 설정해야 합니다.
5. HTTPS가 필요합니다 (Vercel은 자동 제공). Android Chrome의 앱 내 NFC 읽기는 HTTPS에서만 동작합니다.

## NFC 태그 (NTAG 424 DNA SUN)

지점마다 태그 1개를 두고 모든 팀이 같은 태그를 찍습니다. 태그는 찍을 때마다 새 URL을 만들고, 서버는 서명을 검증한 뒤 **한 번 쓴 URL은 다시 받지 않습니다.** 기본적으로 고정 URL·QR·코드 직접 입력으로는 지점이 인정되지 않습니다 (참가 초대 QR은 그대로 사용). 세션별로 고정 QR/URL을 허용하려면 아래 "고정 QR/URL 허용"을 보세요.

### 태그 준비 (행사 전, 1회)

1. 관리자 화면 → 세션 → **NFC** 탭에서 지점을 순서대로 만듭니다.
2. NFC 탭의 "태그 SDM 설정값"에 표시된 값으로 NXP 도구(NXP TagXplorer 또는 TagWriter 등)에서 태그를 설정합니다.
   - NDEF URL: `https://<도메인>/t/s?e=<0 32개>&c=<0 16개>`
   - 암호화 PICCData 미러링(UID + 카운터), SDMMACInputOffset = SDMMACOffset, 암호화 파일 데이터 없음
   - PICCDataOffset / SDMMACOffset: 화면에 표시된 값 (계산값이므로 첫 태그로 반드시 확인)
   - SDM 메타 읽기 키 = `SUN_META_KEY`
   - SDM 파일 읽기 키 = 태그 UID별 키. NFC 탭의 "키 보기"에 UID(14자리)를 넣으면 관리자에게만 표시됩니다
   - 태그의 기본 키(Key0)는 반드시 바꾸고, Random UID는 끄세요.
3. 설정한 태그를 찍어 나온 URL로 지점에 등록합니다.
   - NFC 탭에서 각 지점 줄에 URL을 붙여 넣고 "등록" (Android Chrome은 "NFC로 읽기" 가능)
   - 또는 관리자로 로그인한 휴대폰으로 태그를 찍으면 **관리자 모드** 화면이 열립니다. 세션과 지점을 골라 "등록".
   - 이미 다른 태그가 등록된 지점은 교체 확인을 거칩니다. 같은 세션의 다른 지점에 이미 등록된 태그는 거부됩니다.
4. **실물 리허설:** 설정한 태그를 iPhone과 Android로 각각 찍어 참가자 태깅이 되는지 확인하세요. 오프셋·키 설정은 실물 태그로만 확인할 수 있습니다.

### 행사 당일 절차

1. 태그를 각 지점에 설치합니다.
2. **"레이스 시작" 직전에**, 관리자로 로그인한 휴대폰으로 각 태그를 한 번씩 찍어 "기준 갱신"을 누릅니다 (iPhone·Android 모두 가능).
   - 기준 갱신 이전에 읽힌 URL(행사 전에 누가 미리 모아 둔 URL 포함)은 모두 무효가 됩니다.
   - 기준 갱신 후 시작 전에 찍힌 URL은 유효합니다.
   - 진행 중에 기준을 갱신하면 아직 제출되지 않은 URL이 무효가 되므로, 시작 전에 끝내세요.
3. 관리자 화면에서 "레이스 시작"을 누릅니다.
4. **관리자로 로그인한 기기는 태그를 찍어도 참가자 태깅이 기록되지 않습니다** (관리자 모드가 우선). 레이스에 참가하는 운영진은 관리자 로그아웃하거나 다른 브라우저를 쓰세요.

### 참가자 태깅

- iPhone(XS 이후)과 대부분의 Android는 태그를 대면 브라우저가 열리고 자동으로 제출됩니다.
- 참가 전에 태그를 찍었다면 URL이 보관되었다가 참가·팀 가입 후 한 번 제출됩니다.
- NFC가 안 되는 휴대폰은 팀원 휴대폰으로 찍으면 됩니다 (팀 단위 인정).
- 참고: 관리자가 로그인한 휴대폰으로 태그를 찍으면 등록/기준 갱신 화면이 뜹니다. iOS는 태그가 기본 브라우저(보통 Safari)로 열리므로 관리자 로그인도 그 브라우저에서 해야 합니다.

### 고정 QR/URL 허용 (세션별 스위치)

NTAG 424 DNA가 아닌 일반 태그(NTAG213 등, 고정 URL만 기록 가능)나 인쇄한 QR을 쓰고 싶을 때 세션마다 켤 수 있습니다.

- **먼저 적용:** 운영 DB에 `supabase/migrations/20260928100000_static_tag_switch.sql`을 SQL Editor로 적용한 **뒤에** 이 버전을 배포하세요. 적용 전에는 스위치를 저장할 수 없습니다.
- 관리자 화면 → 세션 → **NFC** 탭의 "고정 QR/URL 허용 (이 세션)"으로 켜고 끕니다. **새 세션과 기존 세션은 모두 꺼져 있습니다.**
- 켜면 지점마다 고정 URL(`https://<도메인>/t/<지점 토큰>`), "URL 복사" 버튼, QR이 표시됩니다.
  - QR을 인쇄하거나, 같은 URL을 아무 NFC 쓰기 앱(NXP TagWriter 등)으로 NTAG213 같은 일반 태그에 기록하세요. 앱에는 NFC 쓰기 기능이 없습니다.
  - URL과 QR은 지금 열어 둔 관리자 화면의 주소로 만들어집니다. **운영 도메인에서 연 관리자 화면에서** 복사·인쇄하세요 (미리보기 주소나 `localhost`로 만든 QR은 행사에서 쓸 수 없습니다).
- 켜진 세션에서는 SUN 태그와 고정 QR/URL을 섞어 쓸 수 있습니다. 순서·중복·완주 규칙은 같고, 한 방식으로 인정된 지점은 다른 방식으로 다시 인정되지 않습니다.
- 꺼진 세션은 지금처럼 SUN 태그만 인정합니다. 진행 중에 꺼도 이미 인정된 기록은 그대로이고, 이후 고정 URL 태깅만 거부됩니다.
- 관리자로 로그인한 기기로 고정 URL을 열면 지점·세션 이름과 스위치 상태만 보여 주는 읽기 전용 화면이 뜹니다 (참가자 태깅 기록 없음).
- **보안 절충:** 켜면 그 세션은 복사·공유 방지가 없습니다.
  - 고정 URL/QR은 사진이나 메시지로 공유되면 현장에 가지 않고도 지점이 인정됩니다.
  - 지점 토큰은 바뀌지 않으므로, 한 번 퍼진 URL/QR은 그 세션의 스위치가 켜져 있는 동안 계속 유효합니다.
  - 고정 URL 태깅에는 횟수 제한이 없습니다. 순서가 틀리거나 중복된 시도는 SUN과 같이 무효 기록으로 남습니다.
  - 부정 방지가 중요한 행사라면 스위치를 끄고 SUN 태그만 쓰세요.

## 참가자 재입장

카카오톡 인앱 브라우저 ↔ Safari 전환 등으로 쿠키를 잃은 참가자는 참가 화면의 **"다시 들어가기"** 탭에서 세션 코드 + 팀 코드 + 이름을 입력하면 기존 참가자로 돌아옵니다 (팀·팀장 여부·진행 기록 유지).

- 이름은 공백과 영문 대소문자 차이를 무시하고 비교합니다.
- 같은 팀 안에서는 같은 이름을 쓸 수 없습니다. 이미 있는 이름으로 팀에 들어가려 하면 "다시 들어가기"를 안내합니다.
- 팀에 들어간 적 없는 참가자는 재입장할 수 없습니다 (새로 참가).
- 종료된 세션에서도 재입장할 수 있습니다.

## 관리자 로그인 제한

- 같은 IP에서 15분 안에 5번을 넘겨 시도하면 15분간 잠깁니다. 잠긴 동안에는 맞는 비밀번호도 거부됩니다. 로그인에 성공하면 횟수가 초기화됩니다.
- 시도 횟수는 Supabase에 저장되어 서버가 여러 대여도 공유됩니다.
- **행사장 와이파이처럼 IP를 여럿이 공유하면** 누군가 틀린 비밀번호를 반복할 때 같은 네트워크의 관리자도 잠길 수 있습니다. 운영진은 모바일 데이터로 접속하는 것을 권장합니다.
- IP는 `X-Forwarded-For` 헤더 기준입니다. Vercel은 이 헤더를 덮어써서 위조할 수 없습니다. Vercel이 아닌 곳에서 `next start`로 직접 운영한다면 앞단 프록시가 이 헤더를 덮어쓰도록 설정해야 합니다.

## 남아 있는 위험

- **새 URL 전달:** 지점에 있는 사람이 태그를 반복해 찍어 매번 새로 생기는 URL을 다른 팀에 보내는 것은 막을 수 없습니다 (태그를 찍을 때마다 새 URL이 생기기 때문). 이미 쓴 URL 재사용과 행사 전 수집은 막힙니다.
- **팀원 분산 배치:** 팀원이 미리 여러 지점에 흩어져 있다가 순서대로 찍는 것은 기술적으로 막지 않습니다 (지점 간 최소 이동 시간 규칙 미적용).
- **재입장 신원 도용:** 세션 코드, 팀 코드, 팀원 이름을 아는 사람은 그 참가자로 들어올 수 있습니다. 재입장에는 시도 횟수 제한이 없어서, 요청을 충분히 보내면 4자리 팀 코드를 추측할 수 있습니다. 두 기기가 같은 참가자로 동작합니다.
- **로그인 제한 우회:** IP를 계속 바꾸는 공격자는 IP당 제한을 우회할 수 있습니다.
- **관리자 쿠키:** 관리자 쿠키는 7일간 유효합니다. 관리자 휴대폰을 잃어버리면 관리자 권한이 함께 노출됩니다.
